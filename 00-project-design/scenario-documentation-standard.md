# Scenario Documentation Standard

**Status:** Shared project standard for all four scenario repositories.  
**Research and documentation standard lead:** [_Lubaba_](https://github.com/lubaba1513-pixel) — Scenario Documentation & Incident Response

This documentation standard was researched, proposed and structured by Lubaba to keep all scenario repositories consistent, reproducible and easy to review across the project.

The infrastructure repository provides the common platform. Each scenario repository must tell the complete SOC story from controlled behavior generation to verified response.

This standard keeps all four exercises comparable without forcing them to use identical detections or dashboards.

## Core rule

Every scenario must be reproducible and reviewable by someone who was not present during the exercise.

A finished scenario should let the reader answer:

1. What behavior was intentionally generated?
2. Which telemetry captured it?
3. How did the detection distinguish it from normal activity?
4. What did the AI suggest, and what did the analyst independently verify?
5. What response was approved?
6. What changed after containment?
7. Which evidence proves the result?

## Required scenario workflow

All scenario repositories must cover the following 20 areas. They can be separate sections or linked documents, but none should silently disappear.

| # | Required area | What it must explain |
|---:|---|---|
| 1 | **Objective** | Security behavior being tested and the learning goal |
| 2 | **Architecture** | Systems, trust boundaries and data paths used by this scenario |
| 3 | **Prerequisites** | Shared services, scenario infrastructure and telemetry that must be healthy first |
| 4 | **Attack / Simulation** | Controlled behavior generated by the Project Lead and the safety boundary |
| 5 | **Telemetry** | Exact DNS, network, endpoint, Web and cloud evidence available |
| 6 | **Detection** | Behavioral hypothesis and what should separate normal from suspicious activity |
| 7 | **SPL / Detection Logic** | Baseline, hunting, detection and validation searches using real fields |
| 8 | **Alert** | Final alert condition, severity/rationale and analyst-ready evidence fields |
| 9 | **AI Triage** | Structured payload sent to the shared AI bridge and returned analyst assistance |
| 10 | **SOC Analysis** | Human investigation, pivots, timeline and final disposition |
| 11 | **Incident Response** | Decision process and approved response steps |
| 12 | **Evidence** | Ground truth, searches, logs, screenshots and response proof |
| 13 | **Containment** | The control actually applied when containment is part of the scenario |
| 14 | **Verification** | Before/after proof that the response had the intended effect |
| 15 | **Results** | What worked, what did not and the final scenario outcome |
| 16 | **MITRE ATT&CK Mapping** | Only techniques genuinely demonstrated by the implemented behavior |
| 17 | **False Positives** | Benign patterns tested and tuning decisions made |
| 18 | **Lessons Learned** | Technical, detection, SOC and IR lessons worth carrying forward |
| 19 | **Reproduction Instructions** | Clean order for another team member to repeat the exercise |
| 20 | **Screenshots** | Curated visual evidence with readable filenames, titles and captions |

## Recommended story flow

The 20 requirements read more naturally when grouped into six phases:

```text
PLAN
Objective → Architecture → Prerequisites

GENERATE
Attack / Simulation → Ground Truth

OBSERVE
Telemetry → Network & Protocol View

DETECT
Dashboard → Baseline → Detection → SPL → Alert → False Positives

INVESTIGATE & RESPOND
AI Triage → SOC Analysis → Incident Response → Containment → Verification

DOCUMENT
Evidence → Results → MITRE → Lessons → Reproduction → Screenshots
```

## Mandatory network & protocol view

This is a DNS project, but the strongest evidence is not limited to a single OSI layer. Every scenario must explain which views were useful and which were not available.

| View | Questions to answer |
|---|---|
| **Layer 7 — DNS** | What name was queried? Which record type? What response/rcode? What answer/TTL/label pattern mattered? |
| **Layer 4** | Was DNS UDP or TCP? Were later HTTP/HTTPS connections involved? Which ports matter? |
| **Layer 3** | Which source/destination IPs were observed? Do VPC Flow Logs support the DNS story? |
| **Endpoint / client** | Which instance/client/process produced the activity when that context is available? |
| **Cloud** | Which Route 53, Resolver or CloudTrail evidence helps establish context? |
| **Application follow-up** | Did the source interact with the Web target or another controlled destination after DNS resolution? |

Do not force every data source into every scenario. Use only the layers that provide real evidence for the behavior being investigated.

## MITRE ATT&CK and Cyber Kill Chain discipline

The locked primary mappings are:

| Scenario | Primary MITRE ATT&CK mapping | Main behavioral phase |
|---|---|---|
| 01 — DNS Reconnaissance | `T1590.002` — Gather Victim Network Information: DNS | Reconnaissance |
| 02 — DGA | `T1568.002` — Dynamic Resolution: Domain Generation Algorithms | Command and Control / dynamic resolution |
| 03 — Fast Flux | `T1568.001` — Dynamic Resolution: Fast Flux DNS | Command and Control / dynamic resolution |
| 04 — DNS Tunneling | `T1071.004` — Application Layer Protocol: DNS; `T1572` only where the implementation fits | Command and Control; later objective only when proven |

The rule is simple: **map what was actually generated, observed and detected.** Do not add techniques just because they sound related.

If a Cyber Kill Chain view is used, label the stage that best describes the demonstrated behavior and explain the evidence. Do not stretch a single controlled DNS exercise across every kill-chain stage.

## Dashboard engineering standard

The dashboards should be useful to an analyst, not just visually busy.

A shared design pattern across scenarios makes the project easier to learn and review:

### Input bar

Use one shared **Time Range** picker for the whole dashboard. Add scenario-relevant filters only when they help investigation, such as:

- source/client;
- DNS query type;
- response code;
- domain/parent domain;
- VPC/instance identity.

### Row 1 — SOC summary

Use 4–6 single-value KPIs that answer the first investigation questions immediately.

Examples include total DNS queries, unique names, NXDOMAIN ratio, distinct query types, unique answer IPs or long-label count depending on the scenario.

### Row 2 — behavior over time

Show the pattern that separates baseline from the scenario behavior. Timecharts are preferred when timing is part of the detection hypothesis.

### Row 3 — DNS patterns

Use bar, column, pie/donut or statistics views only when they make a useful pattern easier to understand: query-type distribution, top names, response codes, TTL distribution, answer churn or label-length buckets.

### Row 4 — correlation

Bring in supporting evidence such as:

- Nginx follow-up requests;
- VPC Flow destinations;
- resolver/client identity;
- endpoint/process context;
- before/after containment data.

### Row 5 — investigation table

Every scenario should have at least one analyst-ready table containing the most useful pivots for raw-event investigation.

### Row 6 — response verification

For scenarios with containment, show the difference between the pre-response and post-response state instead of only showing that an alert fired.

## Scenario dashboard focus

| Scenario | Dashboard questions to emphasize |
|---|---|
| **01 — Recon** | Query rate, record-type diversity, unique names, source identity, response context, Nginx follow-up and VPC Flow follow-up |
| **02 — DGA** | NXDOMAIN count **and ratio**, unique generated names, label length/randomness, client behavior, time pattern and sinkhole before/after |
| **03 — Fast Flux** | Answer/IP churn, TTL behavior, changing destinations, client follow-up connections and containment outcome |
| **04 — Tunneling** | Query frequency, label length/structure, TXT/A behavior, unique subdomains, client identity and before/after containment |

## Dashboard quality rules

- Every panel must answer an investigation question.
- Use real project telemetry and actual field names.
- Do not depend on a pre-labelled `classification="Suspicious"` field unless the lab genuinely creates such a field through its own enrichment process.
- Do not invent threat-intelligence results just to make a dashboard look complete.
- Keep colors consistent and readable, but meaning is more important than decoration.
- Prefer drilldowns or linked searches where they help the analyst move from summary → raw evidence.
- Save the final dashboard source/XML or exported definition in the scenario repository.

## Detection engineering standard

Each scenario should preserve four categories of SPL:

```text
spl/
├── baseline.spl
├── hunting.spl
├── detection.spl
└── validation.spl
```

These files are created only after real searches exist.

### Baseline

Measure normal activity before running the controlled behavior.

### Hunting

Provide analyst pivots that explain the underlying events without assuming an alert already fired.

### Detection

Use the smallest evidence-based logic that identifies the target behavior. Thresholds must come from baseline and controlled testing rather than arbitrary numbers copied from a guide.

### Validation

Prove both sides:

- expected benign activity does not become a high-confidence result;
- the controlled scenario behavior does produce the intended result.

## AI integration standard

The shared AI bridge is common infrastructure. Scenario repositories contain only the **scenario profile / payload mapping** needed after detection fields are stable.

The AI step should receive a structured evidence subset such as:

```text
detection name/version
first/last time
source/client identity
DNS indicators
counts / ratios / query types
response context
related Web / flow context
MITRE candidate
```

The output is analyst assistance, not an automatic verdict. The SOC Analyst must compare it with raw Splunk evidence and record where the summary was correct, incomplete or wrong.

## Incident-response and verification standard

A scenario is not complete because a detection fires.

Where a response is part of the exercise, document:

```text
Finding
  ↓
Human decision
  ↓
Approved containment
  ↓
Expected technical change
  ↓
Observed post-response evidence
```

Examples include a resolver sinkhole response, source isolation, DNS block/deny behavior or removal of temporary controlled infrastructure. The exact response depends on the scenario and the team role.

## Evidence and screenshot standard

Use descriptive filenames and keep screenshots beside the story they prove.

Recommended pattern:

```text
01-architecture-ready.png
02-baseline.png
03-simulation-ground-truth.png
04-detection-trigger.png
05-alert-evidence.png
06-ai-triage.png
07-soc-investigation.png
08-containment.png
09-verification.png
10-final-result.png
```

The exact numbering can grow when a scenario needs more evidence.

For each important screenshot:

1. explain what was configured or tested;
2. show the screenshot;
3. add one short caption explaining what it proves.

Do not use screenshots as a substitute for technical explanation.

## Standard scenario repository shape

The scenario repositories should begin with this structure:

```text
Scenario-XX/
├── README.md
├── SCENARIO-RUNBOOK.md
├── dashboard/
│   └── README.md
├── spl/
│   └── README.md
├── ai/
│   └── README.md
├── ir/
│   └── README.md
├── evidence/
│   └── README.md
└── screenshots/
    └── README.md
```

The README files describe what belongs there. Do not create fake SPL, dashboard XML, AI JSON or evidence before the real work exists.

## Completion condition

A scenario can be marked complete only when the team can reproduce the activity and show a defensible chain:

**Simulation → Telemetry → Detection → Alert → AI Assistance → Human Investigation → Response → Verification → Lessons Learned.**
